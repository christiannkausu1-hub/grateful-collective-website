THE GRATEFUL COLLECTIVE — FUNCTIONAL REPAIR NOTES

Repairs applied to the existing website package:
- Removed the separate legacy pupil, payroll and shop card-collapsing handlers and replaced them with one idempotent card setup. It does not clone headings, does not run a whole-page MutationObserver, and ignores interactive controls so action buttons do not toggle cards. Trade Payables remains excluded.
- Kept the class-list action independent from card toggling.
- Kept Dashboard LEFT TO PAY and Workers & Payroll total on one selected-month unpaid-net-pay calculation.
- Removed NAPSA from ordinary Workers & Payroll entry, calculation, edit modal, payslip and CSV export. Teacher NAPSA return registration remains a separate feature. Existing historical NAPSA database values are not deleted or rewritten.
- Reworked rent-payment save order to create the rental payment, create the linked income transaction, and explicitly check rollback and link-update failures.
- Reworked rent-payment deletion to remove the linked transaction first, then the payment; if payment deletion fails, the transaction is restored and the rental row is relinked to its new transaction ID.
- Preserved all 19 original package files, including assets, manifest, service worker and SQL migration scripts. Every file is at the ZIP root.

Static validation performed:
- ZIP integrity/CRC check passed.
- Inline JavaScript syntax checked with Node.js.
- Duplicate HTML IDs: none found.
- Card handler audit: one card setup system remains; legacy pupil/payroll/shop card setup scripts removed.
- Ordinary payroll NAPSA input/edit field removed; separate teacher return feature retained.

Limitations:
- No live browser interaction test was run.
- No live Supabase/RLS test was run and no SQL migration was executed.
- Multi-table rental operations now perform checked compensating actions, but true atomicity requires a Supabase database RPC/transaction. If the app loses connectivity during a compensating action, manual reconciliation may still be required; the interface reports that failure.
- Existing database records are not modified by building this package.

ADDITIONAL SHOP AUDIT REPAIRS (30 OCTOBER 2026)
- Fixed cancellation refunds so later credit repayments are refunded even when the original credit sale was recorded with zero initial payment.
- Credit repayment RPC now accepts only sales explicitly recorded as Credit.
- Non-credit sales must be fully paid at the time of sale; unpaid balances must be recorded as Credit so customer balances and payment history reconcile.
- Sales reject inactive products at the database level and the product selector hides archived products.
- Product creation now uses an atomic RPC; opening stock creates an opening RESTOCK movement in the same transaction.
- Product names, codes and barcodes have owner-scoped uniqueness indexes when existing data contains no duplicates. Existing duplicate historical data is preserved.
- Manual stock movements are limited to RESTOCK, DAMAGE and EXPIRED. Sales must use the sale workflow; unsupported manual SALE/EXPENSE entries are rejected to prevent movements without matching sale/accounting records.
- Stock movements validate date, quantity precision, money precision, amount calculation and description length. Damage/expiry also create an expense transaction atomically.
- Product editing validates numeric values and offers archive/active control. Existing sale-item unit costs remain historical.
- Shop profit now uses completed sale receipts and saved sale-item costs, excludes cancelled sales, and separately deducts damage/expiry losses.
- Customer credit balances and dashboard arrears include outstanding shop credit. Credit history and receipts show later payment channels and cancellation status.
- Reconciliation rejects future dates and negative/non-cent balances; the dashboard uses the latest reconciliation not later than today.
- Transfer amount/date validation was tightened and transfer history is no longer clipped to 50 rows.
- Fee waivers/adjustments are not automatically inferred: this package does not have an established pupil fee-adjustment schema or verified rules. Existing pupil arrears continue to use configured grade fee less recorded pupil payments.
- Restock movements record stock and cost history, but do not automatically create supplier invoices/payables because supplier-payment terms and the live payable schema must be confirmed separately. Continue recording supplier obligations in Trade Payables.

Those were not duplicated as new patches.
